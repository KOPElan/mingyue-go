# mingyue-go Constitution

## Core principles

### I. 体验一致性优先（CLI 与 API 同源）
- CLI 与 API 必须复用同一套领域能力（同一个包/服务层），禁止复制业务逻辑导致行为漂移。
- 命令与 API 的概念模型保持一致：资源命名、状态枚举、错误码/错误语义一致。
- 输出规范：
	- CLI 默认人类可读；提供 `--json` 输出机器可读 JSON。
	- 错误信息输出到 stderr；成功输出到 stdout；JSON 输出必须结构稳定、可向后兼容。
- 每个功能点必须明确“输入/输出/副作用/权限要求”，并在 CLI 帮助与 API 文档中保持一致。

### II. 代码质量不可妥协（可读、可维护、可审计）
- 遵循 gofmt；公共包和导出符号以“清晰语义”优先。
- 错误必须显式处理；错误信息应可定位（包含关键上下文），但不得泄露敏感信息。
- 平台约束清晰：Linux 专用能力需隔离在明确的包边界内，避免在通用层散落 `runtime.GOOS` 判断。
- 变更必须保持向后兼容：对外 API/CLI 的破坏性变更必须在文档中声明并提供迁移路径。

### III. 测试标准前置（可验证、可回归）
- 新增或修改的对外行为（CLI 命令、HTTP API、输出字段、错误语义）必须有测试覆盖。
- 单元测试使用标准库 `testing`，优先表驱动；关键边界：权限不足、目标不存在、输入非法、并发竞态、超时/中断。
- 集成测试聚焦“系统交互能力”的契约：
	- 进程管理、挂载/卸载、共享管理（samba/nfs）、网络管理等与系统交互的入口需有可重复的验证策略。
	- 对外 API 的路由与响应结构必须有契约测试（至少覆盖成功与典型失败路径）。

### IV. 性能与可靠性基线（可预期、可控）
- 监控类接口应避免高开销操作；优先使用轻量采集方式，必要时做缓存与采样，确保在高频调用下不拖垮系统。
- 长耗时/阻塞系统调用必须支持超时与取消（例如通过 `context` 贯穿），并提供明确的超时错误语义。
- 并发策略清晰：共享状态必须可证明无数据竞争；不得为了吞吐牺牲正确性。
- 对“破坏性操作”（如卸载磁盘、kill 进程、修改共享配置）必须有明确的幂等语义与失败恢复策略（回滚或可重试）。

## Quality gates
- 本地与 CI 的最低质量门禁：`go mod tidy`、`go build ./...`、`go test ./...` 必须通过。
- 新功能合入前必须完成：接口契约确认（CLI/API）、测试覆盖、性能与错误语义自检。

## Governance
- 本宪章高于临时约定；任何与宪章冲突的实现应先修订宪章再落地代码。
- 破坏性变更必须：说明动机、影响面、迁移方案，并在 PR 中显式标注。
