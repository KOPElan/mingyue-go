# ADR-002: CLI 与 API 共享同源业务逻辑层

**状态**: 已接受（Accepted）
**日期**: 2026-02-27
**决策者**: 开发团队

## 背景

mingyue-go 以 CLI 和 HTTP API 两种形态对外提供能力（见 ADR-001）。如果两种形态各自维护一套实现，将面临以下风险：

- **行为漂移**：相同的"查看挂载列表"操作，CLI 与 API 可能因代码分叉而返回不同字段、不同排序或不同错误语义，破坏用户对一致性的信赖。
- **维护成本倍增**：每次功能变更需同时修改两处实现，且任何一处遗漏均可能引入 bug 而不易察觉。
- **测试覆盖分散**：若逻辑分散在两处，需要分别为 CLI 层和 API 层编写重复的逻辑测试，增加无价值的维护负担。

项目宪章（Constitution §I）明确要求：**CLI 与 API 必须复用同一套领域能力，禁止复制业务逻辑导致行为漂移**。

## 决策

建立统一的 **`internal/service/`** 业务逻辑层，作为所有能力的单一来源（Single Source of Truth）：

```
internal/
├── service/
│   ├── system/      # 系统监控（CPU/内存/磁盘概览）
│   ├── process/     # 进程查询与管理
│   ├── disk/        # 磁盘与挂载管理
│   ├── file/        # 文件管理（含路径安全校验）
│   └── share/       # 共享管理（Samba/NFS）
├── cli/             # CLI 子命令处理器（仅负责参数解析与输出格式化）
└── api/             # HTTP API 处理器（仅负责请求解析与响应序列化）
```

**分层原则**：
- `internal/service/` 包含所有业务逻辑、权限校验、审计日志触发逻辑。
- `internal/cli/` 仅负责：解析 cobra 命令参数 → 调用 service 层 → 格式化输出（人类可读或 `--json`）。
- `internal/api/` 仅负责：解析 HTTP 请求 → 调用 service 层 → 序列化 JSON 响应。
- `internal/domain/` 定义纯数据结构（无业务逻辑），供 service/cli/api 层共享引用。

CLI `--json` 输出与 API 响应在核心数据字段上必须对齐，并通过契约测试锁定。

## 备选方案

| 方案 | 描述 | 拒绝原因 |
|------|------|----------|
| CLI 与 API 各自实现 | 两种形态分别维护独立的业务逻辑 | 行为漂移不可避免；维护成本与 bug 风险均倍增（被宪章明确禁止） |
| API 层调用 CLI 子进程 | API handler 通过执行 CLI 二进制获取结果 | 引入进程生命周期开销、序列化/反序列化开销；错误处理复杂；不适合高频 API 调用场景 |
| CLI 层调用 API 接口 | CLI 命令均通过本地 HTTP 请求转发给守护进程 | 守护进程未运行时 CLI 完全不可用；引入不必要的网络依赖；违背"直接执行"的设计目标 |

## 后果

### 正面影响
- CLI 与 API 对同一操作的行为天然一致，不存在漂移风险。
- 业务逻辑（权限校验、幂等语义、审计日志）仅需实现一次，降低维护成本。
- 单元测试聚焦于 service 层，无需为 CLI/API 适配层重复覆盖业务规则。
- 新增功能时，只需实现 service 层接口，CLI/API 处理器仅做"胶水"工作，开发效率提升。

### 负面影响 / 权衡
- service 层接口设计需要同时兼顾 CLI 的"批处理/本地调用"语义与 API 的"HTTP 请求/响应"语义，需要在设计阶段投入更多思考。
- service 层函数签名变更会同时影响 CLI 和 API handler，需要严格遵循向后兼容原则。
- `internal/` 包可见性约束确保了正确的封装，但跨包测试时需注意接口边界。
