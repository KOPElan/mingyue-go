# ADR-006: 审计日志设计

**状态**: 已接受（Accepted）
**日期**: 2026-02-27
**决策者**: 开发团队

## 背景

mingyue-go 管理的操作涉及多种系统变更，包括：挂载/卸载磁盘、终止进程、创建/删除/移动文件、创建/修改/删除共享配置等。这些操作具有以下特点：

- **不可轻易撤销**：挂载点变更、文件删除、共享配置变更可能对业务造成直接影响。
- **多来源触发**：同一操作可能由 CLI 本地执行或通过 API 远程触发，需要区分来源。
- **合规审计需求**：安全/合规审计人员需要能够事后追溯"谁、在何时、对什么对象、执行了什么操作、结果如何"。
- **敏感信息保护**：审计日志不得包含 CIFS 密码、API 密钥、共享访问凭据等敏感信息。

如果没有结构化的审计日志，操作溯源依赖系统日志（如 journald/syslog），信息分散且格式不一致，难以用于合规检查或故障排查。

## 决策

在 **`internal/audit/`** 包中实现集中化的结构化审计日志系统：

### 审计事件结构

```go
// AuditEvent 表示一次可审计的操作事件
type AuditEvent struct {
    Timestamp   time.Time `json:"timestamp"`            // RFC3339 格式时间戳
    Source      string    `json:"source"`               // "cli" 或 "api"（含客户端 IP/用户）
    Actor       string    `json:"actor"`                // 操作者标识（角色/用户名/API token ID）
    Operation   string    `json:"operation"`            // 操作类型（如 "disk.mount"、"process.kill"）
    Target      string    `json:"target"`               // 操作目标（如挂载点路径、PID、共享名）
    Result      string    `json:"result"`               // "success" 或 "failure"
    ErrorCode   string    `json:"error_code,omitempty"` // 失败时的错误码
    ErrorMsg    string    `json:"error_msg,omitempty"`  // 失败时的错误描述（不含敏感信息）
    RequestID   string    `json:"request_id,omitempty"` // 可选：API 请求 ID，便于关联链路
}
```

### 审计范围

以下操作类型**必须**记录审计事件（无论成功或失败）：

| 操作域 | 需审计的操作 |
|--------|-------------|
| 进程管理 | 终止进程（kill）、发送信号 |
| 磁盘管理 | 挂载、卸载（本地/CIFS/NFS） |
| 文件管理 | 创建文件/目录、删除、移动、复制、写入 |
| 共享管理 | 创建共享、修改共享、删除共享 |
| 权限/ACL（P1） | 设置文件权限、设置 ACL |
| 网络管理（P1） | 网络接口变更、DHCP 刷新 |

只读查询操作（如查看进程列表、查看挂载列表）不在审计范围内（降低日志噪音）。

### 日志存储与格式

- **格式**：JSON Lines（每行一个 JSON 对象），便于流式处理与 grep 检索。
- **写入目标**：`/var/log/mingyue/audit.log`（守护进程模式）；CLI 模式下写入同一文件（若有写权限）或 stderr。
- **日志轮转**：依赖系统级 `logrotate` 配置，不在程序内实现，避免不必要的复杂度。

### 敏感信息保护

- CIFS 凭据（用户名/密码）、API token、共享访问密钥等**绝不写入**审计日志。
- `Target` 字段记录挂载点路径而非凭据；CIFS 操作审计记录中主机/共享路径保留，凭据字段用 `"[REDACTED]"` 占位（如有需要展示）。
- 文件操作不记录文件内容，仅记录路径与操作类型。

### 触发位置

审计事件在 `internal/service/` 层触发（而非在 CLI/API handler 层），确保无论通过哪种形态触发的操作都被审计覆盖。

## 备选方案

| 方案 | 描述 | 拒绝原因 |
|------|------|----------|
| 依赖系统日志（journald/syslog） | 将所有操作日志写入 syslog，依赖系统工具审计 | 格式不结构化，难以按"操作类型/目标/结果"过滤；与程序日志混合，信噪比低 |
| 使用关系数据库存储审计记录 | 将 AuditEvent 写入 SQLite/PostgreSQL | 引入额外的存储依赖；守护进程部署复杂度上升；超出当前 v1 范围的简洁性要求 |
| 在 CLI/API handler 层触发审计 | 在请求进入/离开时记录审计 | CLI 与 API 需各自实现，容易遗漏；业务逻辑变更时审计点维护困难 |
| 仅记录失败审计 | 只记录失败操作 | 成功的高危操作（如成功终止进程）同样需要追溯；"成功但未授权"的场景无法被发现 |

## 后果

### 正面影响
- JSON Lines 格式便于使用标准工具（jq、grep、ELK Stack）检索与分析。
- 统一的 `AuditEvent` 结构使审计日志可靠、可预期，安全审计人员无需适应多种格式。
- 在 service 层触发确保 CLI/API 两种形态的操作均被覆盖，不遗漏。
- 明确的"不含敏感信息"约束，从设计上防止凭据泄露到日志文件。

### 负面影响 / 权衡
- 所有高危操作路径需要主动调用审计日志写入，若有遗漏则覆盖不完整，需在 code review 与测试中重点关注。
- 审计日志文件需要妥善保护（权限设置），否则可能暴露操作目标（如挂载路径、共享名）。
- JSON Lines 格式对于非结构化场景的快速 grep 略显繁琐，但长期可维护性优于纯文本。
- 日志轮转依赖外部 `logrotate` 配置，需要在安装脚本（`install.sh`）中提供示例配置。
