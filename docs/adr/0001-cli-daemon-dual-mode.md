# ADR-001: 采用 CLI + 守护进程双运行形态

**状态**: 已接受（Accepted）
**日期**: 2026-02-27
**决策者**: 开发团队

## 背景

mingyue-go 面向两类核心用户场景：

1. **运维/开发人员直接操作**：在终端以命令行方式快速完成系统监控、进程管理、磁盘挂载、文件管理等操作，无需部署任何服务。
2. **上层平台集成**：Web 可视化平台或自动化工具需要通过标准化 HTTP+JSON API 持续访问主机能力，要求代理以常驻进程形式运行并暴露 RESTful API。

这两种场景对运行形态的需求截然不同：CLI 要求"下载即用、零依赖"；API 要求"开机自启、稳定监听"。如果只提供其中一种，将无法同时满足这两类场景，也无法体现"单一二进制、多形态交付"的工程价值。

## 决策

采用 **CLI + 守护进程双运行形态**，两者均由同一个 Go 二进制文件承载：

- **CLI 模式**：使用 [cobra](https://github.com/spf13/cobra) 构建子命令框架，用户直接执行二进制即可完成操作，无需常驻服务。根命令注册全局 `--json` flag，支持机器可读输出。
- **守护进程模式**：通过 `mingyue agent start` 启动守护进程，监听 HTTP 端口提供 RESTful API（路径前缀 `/api/v1`）。提供 `install.sh` 脚本将其注册为 **systemd service**，实现开机自启与系统级管理。
- 两种形态均调用同一套 `internal/service/` 业务逻辑层，禁止逻辑分叉（见 ADR-002）。

守护进程通过 PID 文件管理进程生命周期，处理 `SIGTERM`/`SIGINT` 信号以优雅退出。

## 备选方案

| 方案 | 描述 | 拒绝原因 |
|------|------|----------|
| 仅提供 CLI | 不提供守护进程与 API | 无法满足平台集成与持续监控的需求（GH-002、GH-003） |
| 仅提供 HTTP API 服务 | 所有操作均通过 HTTP 完成 | 运维人员需要额外的 HTTP 客户端工具，操作门槛高，无法"直接执行" |
| CLI 与 daemon 为独立二进制 | 分别构建 CLI 工具和 API 服务 | 增加发布与维护复杂度；更容易造成行为漂移 |
| 使用 launchd / SysV init | 替代 systemd 的守护进程管理 | 目标平台明确为 Linux 主流发行版（Ubuntu/Debian/RHEL/CentOS），systemd 已成为事实标准；launchd 属于 macOS，SysV init 逐步淘汰 |

## 后果

### 正面影响
- 运维人员可在无网络/无服务依赖的场景下直接使用 CLI，降低使用门槛。
- 守护进程提供稳定的 HTTP API，满足平台集成与可视化管理需求。
- 单一二进制简化分发与部署，降低版本一致性风险。
- systemd 集成使守护进程具备开机自启、日志收集（journald）、资源限制等系统级能力。

### 负面影响 / 权衡
- 守护进程未运行时，CLI 对某些需要服务协调的操作需要降级处理或给出明确提示，增加一定的状态感知复杂度。
- `install.sh` 需要覆盖不同 Linux 发行版的差异（systemd unit 路径、权限等），维护成本略高。
- 双形态需要额外测试覆盖（CLI 直接执行 vs. 通过 API 访问），但共享业务逻辑层可显著降低重复测试成本。
