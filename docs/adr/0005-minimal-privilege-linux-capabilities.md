# ADR-005: 最小权限原则与 Linux Capabilities

**状态**: 已接受（Accepted）
**日期**: 2026-02-27
**决策者**: 开发团队

## 背景

mingyue-go 涉及多种系统级操作，其中部分操作具有较高的安全风险：

- **挂载/卸载**（本地磁盘、CIFS、NFS）：需要 `CAP_SYS_ADMIN`。
- **终止任意进程**：需要对目标进程有信号发送权限（通常需要与目标进程同 UID 或 root）。
- **SMART 信息获取**：`smartctl` 需要访问原始磁盘设备，通常需要 root 或 `CAP_SYS_RAWIO`。
- **Samba/NFS 共享配置变更**：需要写入系统配置文件（`/etc/samba/`、`/etc/exports`）并重载服务。
- **网络接口管理**（P1）：需要 `CAP_NET_ADMIN`。

如果守护进程以 root 身份运行，则任何对该进程的漏洞利用都具有对整个系统的完全控制权，违背"最小权限"安全原则。另一方面，如果完全以非特权用户运行，上述高危操作将无法完成。

需要在"功能完整性"与"安全边界"之间找到平衡点，同时对用户明确说明哪些功能需要哪些权限。

## 决策

遵循 **最小权限原则（Principle of Least Privilege）**，具体落地策略如下：

### 运行权限分级

| 操作类型 | 最低所需权限 | 说明 |
|----------|-------------|------|
| 只读监控（CPU/内存/磁盘/进程列表） | 普通用户 | 可在完全非特权模式下工作 |
| 终止本用户进程 | 普通用户 | 仅限同 UID 进程 |
| 终止任意进程 | root 或 `CAP_KILL` | 需要显式权限提升 |
| 挂载/卸载本地磁盘 | `CAP_SYS_ADMIN` | |
| 挂载/卸载 CIFS/NFS | `CAP_SYS_ADMIN` | |
| SMART 信息获取 | `CAP_SYS_RAWIO` 或 root | 建议配合 `smartctl --device` 使用 |
| Samba/NFS 共享配置变更 | root（写配置文件）或专用服务账户 | |
| 文件读写（白名单目录内） | 普通用户（视目录权限） | |
| 网络接口管理（P1） | `CAP_NET_ADMIN` | |

### 守护进程运行方式

- **默认**：以专用低权限系统账户（如 `mingyue`）运行，禁用不必要的能力。
- **高危操作**：通过 Linux capabilities 按需授权，避免以完整 root 身份运行。
  - 安装时由 `install.sh` 通过 `setcap` 或 systemd `AmbientCapabilities` 配置最小化能力集。
- **权限不足时**：返回 `AppError{Code: PERMISSION_DENIED}`，明确提示所需权限（capabilities 或 root），不静默失败。

### 代码层隔离

- 所有 Linux 特权系统调用封装在 `pkg/linux/` 包中，与业务逻辑层分离。
- `pkg/linux/capabilities.go` 提供运行时能力检测函数，在操作执行前进行权限预检。
- 高危操作执行前记录审计日志（见 ADR-006）。

### 文档承诺

- 项目文档明确列出每个功能所需的最低权限（capabilities 或 root），作为用户和运维人员的参考。
- `install.sh` 中的权限配置有注释说明每项 capability 的用途。

## 备选方案

| 方案 | 描述 | 拒绝原因 |
|------|------|----------|
| 始终以 root 运行 | 守护进程以 root 身份运行，无需权限管理 | 安全风险最大：任何漏洞均可导致完全系统控制权丧失；违背安全基线 |
| setuid 二进制 | 将二进制设置为 setuid root | setuid 是粗粒度的全量权限提升，无法精确控制；调试复杂；现代 Linux 推荐 capabilities 替代 |
| 完全非特权运行，高危操作不支持 | 放弃高危操作支持 | 无法满足 PRD 中磁盘管理、共享管理等 P0 功能需求 |
| sudo 封装 | 通过 `sudo` 执行特权命令 | 依赖外部 sudoers 配置；在守护进程场景中 sudo 交互式提示不可用；安全审计困难 |

## 后果

### 正面影响
- 守护进程以最小权限运行，即使存在漏洞，影响范围也被限制在最小化的能力集内。
- Linux capabilities 提供细粒度的权限控制，优于粗粒度的 root/非 root 二元模型。
- 权限预检机制确保权限不足时快速失败（fail-fast），而非在操作过程中以不可预期的方式失败。
- 文档化的权限需求使运维人员和安全审计人员可以对系统权限边界进行明确评估。

### 负面影响 / 权衡
- 不同 Linux 发行版对 capabilities 的支持和配置方式存在差异，`install.sh` 需要处理兼容性问题。
- `AmbientCapabilities`（systemd）在较旧的内核版本上可能不支持，需要提供降级方案（如 `setcap`）。
- 对于某些需要多种 capabilities 组合的操作（如同时需要 `CAP_SYS_ADMIN` 和磁盘访问），权限管理的复杂度上升。
- 开发和测试环境中需要模拟权限不足场景，增加测试配置复杂度。
