## PRD: Mingyue Linux 系统操作代理

## 1. 产品概述

### 1.1 文档标题与版本

- PRD: Mingyue Linux 系统操作代理
- Version: 0.2.0

### 1.2 产品简介

本项目旨在使用 Go 实现一个面向 Linux 主机的“系统操作代理（agent）”，以两种形态对外提供能力：
1）面向运维/开发人员的 CLI 命令行工具，用户可在终端以简单命令完成系统监控、进程管理、磁盘与挂载管理、文件管理、共享管理等操作；
2）面向 Web 端或其他平台的标准化 RESTful HTTP+JSON API，作为可视化管理系统的后端能力提供方（Web 前端不在本项目范围）。

项目需要支持“直接执行二进制”与“安装为常驻守护进程”两种运行模式。对于涉及系统级变更的操作，必须遵循最小权限原则，仅在必要时以 root 或必要 Linux capabilities（例如 CAP_SYS_ADMIN、CAP_NET_ADMIN）运行或提升。

项目的标准 API 交付物必须包含 OpenAPI/Swagger 规范，以便第三方自动生成客户端或对接可视化平台。

## 2. 目标

### 2.1 业务目标

- 提供可复用、标准化的 Linux 主机管理能力，作为上层可视化管理的基础组件。
- 通过 CLI 降低常见运维操作的复杂度与学习成本。
- 通过“最小权限 + 可审计”的方式降低系统操作风险。

### 2.2 用户目标

- 用户可在终端用一致的命令快速查看主机状态并管理进程/磁盘/文件/共享。
- 平台可通过稳定的 HTTP+JSON API 获取监控数据并发起管理动作。
- 在安全边界清晰的前提下完成高危操作（挂载/卸载、共享配置变更等）。

### 2.3 非目标

- 不提供 Web UI 与可视化前端。
- 不覆盖非 Linux 平台（Windows/macOS）。
- 不做跨主机的集中化调度/编排（仅作为单机 agent 能力）。
- 不承诺替代成熟监控系统的全部能力（如全量 APM、分布式追踪）。

## 3. 用户画像

### 3.1 关键用户类型

- 运维工程师：需要通过 CLI 快速定位主机问题并执行管理动作。
- 平台开发/集成工程师：需要通过 API 与 OpenAPI 规范集成到 Web 管理端。
- 安全/合规审计人员：关注权限边界、操作审计与变更追踪。

### 3.2 画像说明

- **运维工程师**：偏好简单、可靠、可复制的命令；关注输出稳定、错误可读、执行可回滚。
- **平台开发/集成工程师**：偏好稳定的 REST API、清晰的错误码、完善的 OpenAPI 文档。
- **安全/审计人员**：偏好最小权限、明确的高危操作保护与可审计日志。

### 3.3 基于角色的访问控制

- **只读（viewer）**：允许读取监控与状态（CPU/内存/磁盘/进程列表、挂载列表、共享状态等）。
- **操作员（operator）**：在只读基础上允许执行低风险操作（例如终止指定进程需额外限制；文件读写需目录白名单或权限校验）。
- **管理员（admin）**：允许执行高风险系统变更（挂载/卸载、共享配置变更等），需额外的鉴权与审计。

## 4. 功能需求

- **运行形态：CLI + 守护进程 + API** (Priority: P0)
  - 支持直接执行二进制完成操作。
  - 提供 `install.sh`（或等效安装方式）安装为常驻守护进程（建议兼容 systemd）。
  - 守护进程提供 RESTful HTTP+JSON API。
  - CLI 与 API 必须复用同源业务逻辑，确保行为一致。

- **系统监控与进程管理** (Priority: P0)
  - 提供 CPU、内存、磁盘使用率、进程列表与关键指标读取能力。
  - 提供进程管理能力（至少：按 PID 查询、终止进程；可扩展：发送信号、按名称过滤）。
  - 高风险操作（kill）必须有明确权限要求与审计日志。

- **磁盘管理** (Priority: P0)
  - 支持挂载/卸载本地磁盘。
  - 支持 CIFS/NFS 挂载/卸载。
  - 支持获取 SMART 信息（至少：基础健康状态、关键属性读取；在无权限/无工具时返回可解释错误）。
  - 对卸载与挂载失败需给出可定位原因与可重试策略。

- **文件管理** (Priority: P0)
  - 文件/目录列表、元信息查询（大小、时间、权限）。
  - 基础文件操作（创建/删除/移动/复制、读写）。
  - 权限相关操作需遵循最小权限与路径安全约束（例如避免目录穿越）。

- **共享管理（samba、nfs）** (Priority: P0)
  - 支持查询共享状态与配置摘要。
  - 支持创建/修改/删除共享（以最小可用集为目标，避免一次性覆盖所有高级参数）。
  - 变更必须可审计，并提供失败回滚或明确的恢复步骤。

- **Docker 管理** (Priority: P0)
  - 支持查询 Docker daemon 可用性与版本信息。
  - 支持容器只读查询（列表、详情、资源占用摘要）。
  - 支持受控的容器生命周期管理（启动/停止/重启）。
  - 支持拉取与删除镜像等高风险操作（默认仅 admin），并记录审计日志。
  - 任何 Docker 相关接口必须明确权限要求，并在权限不足/daemon 不可用时返回可解释错误。
  - 默认不提供“创建/运行新容器（等价 docker run）”“修改宿主 Docker 全局配置”等能力（如需纳入，需在后续版本单独评审安全边界）。

- **网络管理** (Priority: P1)
  - 支持查询网络接口、地址、路由等基础信息。
  - 支持常见网络管理动作（在安全边界下逐步开放，例如启停接口、刷新 DHCP 等）。
  - 所有变更操作必须有明确权限要求、幂等语义与审计日志。

- **用户权限与 ACL** (Priority: P1)
  - 支持查询用户/组信息与关键权限概览。
  - 支持文件/目录权限与 ACL 的查询与设置（在路径安全与最小权限约束下）。
  - API 必须区分只读与变更能力，并提供审计。

- **标准 API 与 OpenAPI 交付物** (Priority: P0)
  - 所有 API 使用 HTTP+JSON，遵循一致的版本前缀（例如 `/api/v1`）。
  - 提供 OpenAPI/Swagger 规范文件作为交付物（例如 `openapi.json`/`openapi.yaml`），并与实现保持同步。
  - 错误响应结构稳定，包含可机器解析的错误码与人类可读信息。

- **最小权限与安全边界** (Priority: P0)
  - 默认以最低权限运行；仅在必要场景提升权限或以 capabilities 运行。
  - 对高危接口提供鉴权与授权策略（详见用户故事）。
  - 记录关键管理操作的审计日志。

## 5. 用户体验

### 5.1 入口与首次使用流程

- 下载/构建二进制并直接运行 CLI。
- 可选：执行 `install.sh` 安装守护进程并启动服务。
- 首次使用 API：获取 OpenAPI 文档并通过示例请求验证连通性。

### 5.2 核心体验

- **查看主机状态**：用户通过 CLI 或 API 获取 CPU/内存/磁盘/进程概览
  - 输出一致、信息聚合清晰、默认快速返回。
- **处理异常进程**：用户定位占用高的进程并终止/发送信号
  - 明确风险提示与权限要求；失败原因可定位。
- **挂载远端共享**：用户通过 CLI/API 挂载 CIFS/NFS 并验证挂载点
  - 支持幂等；失败给出下一步建议（凭据、网络、权限、目标路径）。
- **管理文件与共享**：用户创建目录、修改共享配置并验证生效
  - 变更可审计；提供回滚或恢复策略。

- **管理容器与镜像**：用户查看容器运行状态，必要时重启容器并拉取镜像
  - 对高风险操作进行授权与审计；错误信息可定位（daemon 不可用、权限不足、容器不存在、拉取失败等）。

### 5.3 进阶能力与边界场景

- 守护进程未运行时，CLI 可自动降级为本地执行模式或给出明确提示。
- 目标资源不存在（PID、文件路径、挂载点）时返回稳定错误码。
- 权限不足时返回可解释错误并提示所需权限（root/capabilities）。
- 操作被取消或超时时，返回可重试且不破坏系统一致性的结果。
- Docker daemon 未安装、未运行或 socket 不可访问时，Docker 相关命令/接口返回可解释错误与恢复建议。
- 容器日志可能非常大：必须支持限制行数/字节数或时间窗口，避免一次性返回导致内存压力。

### 5.4 体验要点

- CLI 输出默认人类可读；提供 `--json`，便于脚本化。
- API 响应结构稳定，便于 Web 端渲染与自动化对接。
- 错误信息可定位但不泄露敏感信息（口令、密钥、完整配置内容）。

## 6. 用户旅程叙述

用户在终端通过统一命令快速了解主机运行状态，遇到异常时能定位问题进程、检查磁盘与挂载、管理文件与共享；当服务以容器方式部署时，也能查看容器状态并执行受控重启、拉取镜像等操作。同一套能力可通过 REST API 被上层平台调用，实现可视化与自动化运维。在最小权限与审计日志的约束下，系统变更可控、可追溯、可回归。

## 7. 成功指标

### 7.1 用户侧指标

- 常见任务（查看资源、列进程、挂载/卸载、文件操作）平均完成时间降低。
- CLI 命令的学习成本降低（帮助信息清晰、参数一致）。
- API 对接效率提升（OpenAPI 可生成客户端，集成时间降低）。

### 7.2 业务侧指标

- 作为基础 agent 组件的复用次数/接入项目数。
- 上层平台对接稳定性（兼容性问题数量下降）。

### 7.3 技术指标

- 监控类接口 P95 延迟（例如 < 200ms 的目标，可在实现阶段细化）。
- 守护进程资源占用（CPU/内存）在空闲与高频调用下可控。
- Docker 只读查询（容器列表/详情）P95 延迟目标（例如 < 500ms，可在实现阶段细化）。
- `go test ./...` 通过率 100%，关键路径测试覆盖率提升。

## 8. 技术考量

### 8.1 集成点

- Linux 系统信息来源（如 `/proc`、`/sys`、系统命令或 netlink 等），需在实现阶段选型并封装。
- systemd 集成（守护进程安装与管理）由 `install.sh` 或等效方式完成。
- samba/nfs 的配置与服务管理需明确依赖（系统服务存在、配置文件路径、重载方式）。
- Docker 集成：优先使用 Docker Engine API（通过 Unix socket，例如 `/var/run/docker.sock`）；如需兼容性降级，可选用调用 `docker` CLI 的方式（需明确依赖与输出解析风险）。

### 8.2 数据存储与隐私

- 配置与状态文件建议区分：配置（例如 `/etc/...`）、状态（例如 `/var/lib/...`）、日志（例如 `/var/log/...`），具体路径在实现阶段确认。
- API 凭据（若使用）不得明文写入日志；如需落盘应考虑权限与加密策略。

### 8.3 可扩展性与性能

- 监控类请求需避免高开销扫描；必要时做缓存与采样，保证高频调用场景下稳定。
- 长耗时系统调用需支持超时与取消（建议使用 `context` 贯穿）。

### 8.4 潜在挑战

- 最小权限落地：CAP_SYS_ADMIN/CAP_NET_ADMIN 等能力边界、不同发行版差异。
- samba/nfs 配置变更的兼容性与回滚策略。
- SMART 信息获取可能依赖系统工具/设备权限，需提供降级与清晰错误。
- Docker 权限与安全边界：访问 Docker socket 通常等价于 root 权限，需在部署与授权上有明确策略（例如仅在需要 Docker 管理时启用、限制为 admin 角色、强制审计）。
- Docker 生态差异：rootless Docker、containerd/CRI 环境、不同发行版/版本在 API 行为与权限上的差异。

## 9. 里程碑与推进顺序

### 9.1 项目预估

- M：4-8 周（以 v1 范围为准，具体视共享管理复杂度调整）

### 9.2 团队规模与构成

- 1-2 人：Go 开发（系统编程）+ 测试/文档

### 9.3 建议阶段划分

- **Phase 1**: 基础骨架与运行形态（2 周）
  - CLI 框架、守护进程框架、HTTP API 基础、统一错误结构、权限模型草案。
- **Phase 2**: 监控+进程（2 周）
  - 指标采集与进程管理能力、CLI/API 对齐、基础测试。
- **Phase 3**: 磁盘管理（2 周）
  - 挂载/卸载、CIFS/NFS 挂载、SMART 读取、幂等与回滚策略。
- **Phase 4**: 文件管理 + 共享管理（2 周+）
  - 文件操作与路径安全、samba/nfs 共享查询与变更、审计日志完善。

- **Phase 5**: Docker 管理（1-2 周）
  - Docker daemon 探测、容器/镜像查询、容器启停重启、镜像拉取/删除（受控）、审计日志与权限模型对齐。
